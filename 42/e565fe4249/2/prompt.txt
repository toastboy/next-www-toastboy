Structure, outside-in:

2. **`src/app/footy/layout.tsx`** — segment layout, adds only `&lt;SearchParamErrorNotification /&gt;`, no layout/width markup.
3. **`page.tsx`** (`PlayerPage`, server component) — does data-fetching only; renders `&lt;AutoRefresh&gt;` + `&lt;PlayerProfile ...&gt;` inside a bare fragment (`&lt;&gt;...&lt;/&gt;`). **No `Container`, `Paper`, or width constraint at the page level at all.**
4. **`src/components/PlayerProfile/PlayerProfile.tsx`** — the actual layout lives here:
   - Root: `&lt;Stack gap="sm" w="100%"&gt;` — full width, no max-width, no wrapping `Paper`/`Container`.
   - Row 1: `&lt;Grid type="container" mb="lg" gap="xs" align="center"&gt;` with 3 `GridCol`s — prev-player arrow (`span="content"`), centered `&lt;TitleWithYearDropdown&gt;` (`span="auto"`), next-player arrow (`span="content"`).
   - Row 2: `&lt;Grid type="container" breakpoints={{...}}&gt;` with 4 `GridCol`s (`span={{ base: 12, sm: 6, lg: 3 }}`) each containing one card-style component: `PlayerCard`, `PlayerInfo`, `PlayerResults`, `PlayerPositions`.
   - Row 3: `&lt;Group&gt;` wrapping a single `&lt;Paper p="sm" w="auto" withBorder style={{ flex: '1' }}&gt;` containing `&lt;PlayerHeatmap&gt;`.

So the "wrong way" this ticket likely refers to: the page renders **full-bleed** (only constrained by the app-shell's `fluid` container plus its own `padding` prop), with **no `&lt;Container size="..."&gt;`** anywhere in the profile's own tree to cap line-length/card-grid width on ultra-wide screens, while several *other, simpler* pages (signin, forgottenpassword, response, claim, tables, countrymap, admin) instead hard-code ad hoc `maw="35rem"` Paper wrappers directly in the page file rather than using `Container`. ## The Recommendation

Adopt the corrected rule, not the proposed one. The proposed rule is directionally right (components own width) but structurally wrong in two specific, fixable ways: it omits maximum-width, and it hands pages a sizing responsibility that has never existed in this codebase and would recreate today's bug the moment someone acts on it literally.

**Final rule to put in CLAUDE.md:**

&gt; Every visually-rendering component that must be independently renderable (standalone, in Storybook, under test) owns its own width and chrome — fixed, minimum, *and* maximum (`Container`, `Paper`, `w`/`miw`/`maw`) — because it must render correctly with zero cooperation from whatever renders it. Pages compose components and pass data; they make no sizing or wrapping decisions of any kind. The one exception is flex/grid-child components (e.g. `Turnout`, `WinnersTable`) that declare `miw`/`maw` but deliberately omit an outer `Container`, expecting a parent Grid/Flex — that parent is itself a component, never a page. A page file containing `&lt;Container`, `&lt;Paper w=`, or an explicit width prop should fail review on sight.

This keeps E's structural insight (pages are composition roots, not a layout tier) as the reasoning, keeps C's catch (maximum width belongs in the vocabulary) as the content fix, keeps B's enforceable phrasing as the operative clause, and names the third pattern explicitly per C/D so it isn't "fixed" by someone adding an unneeded `Container` later. D's three-tier taxonomy is noted but not adopted — revisit it only if a genuine composite-layout component (distinct from a leaf) actually shows up.

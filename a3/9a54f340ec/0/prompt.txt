### Assessment: can one `StatusNotification` component cover all 10?

Not cleanly with a single trivial `{message, color, icon, variant, anchor}` API — there are real structural differences to account for:

- **Two distinct rendering families**: `Notification`-based (files 1,2,3,4,5,6,7,8 — 8 of 10) vs plain `Text`(+`Anchor`)-based with no icon/notification chrome at all (files 9 and 10). A shared component would need a `variant: 'notification' | 'text'` prop (matching the "Box+Text+Anchor variant" the prompt anticipated) to cover 9 and 10, or those two could reasonably be left out of the shared component (they're not really the same visual pattern — no icon, no colored notification box).
- **`withCloseButton`**: explicitly `false` in files 3,4,5,6; left at default (`true`) in files 1,2,7,8. Needs to be a prop (default true, override false) — not a hardcoded constant.
- **Anchor is optional and varies**: absent in 1,2,3,7,8,9(has one)/10(has one); present in 4,5,6 (all `red`/error) each with different `href`/label (`/footy` "Return to the home page" ×2, `/footy/profile` "Return to your profile"); present in 9/10 style too. So `anchor?: { href: string; label: string }` fits well for the `Notification`-family files that have one (4, 5, 6) plus the two `Text` outliers (9 doesn't have an anchor, 10 does).
- **Message content type varies**: literal hardcoded JSX text (1, 7, 8) vs dynamic string variables from `toPublicMessage()` (3, 4, 5 error branch, 6, 9). A `message: React.ReactNode` prop handles both.
- **Color/icon pairing varies**: `red`+`IconX` (2,3,4,5 err,6,7,8), `blue`+`IconX` (1 — non-error info), `teal`+`IconCheck` (5 success). So `color` and `icon` must be independent props, not derived from a single `severity` enum, unless you add a `'blue'` info variant.
- **Wrapping context differs**: standalone (1,2,3,7,8) vs wrapped in `&lt;Stack&gt;` with a sibling `&lt;Anchor&gt;` (4,5,6) — but this is just consumption-side layout, easily handled by having the shared component itself optionally render the anchor internally (via the `anchor` prop) rather than requiring callers to wrap in `Stack`.
- **File 5 is the only site needing two calls of the component** (error state and success state) in the same page — not a structural blocker, just confirms the component must support both colors/icons via props rather than being error-only.
- **Files 9 and 10 have no icon/Notification chrome at all** — forcing them into a `Notification`-styled shared component would change their visual appearance unless the component supports a `variant='plain'` (bare colored `Text` + optional `Anchor`, no `Notification` box) as literally the "Box+Text+Anchor" variant mentioned in your prompt.

**Conclusion**: A `StatusNotification` component with props like `{ variant: 'notification' | 'plain', message: ReactNode, color: MantineColor, icon?: ReactNode, withCloseButton?: boolean, anchor?: { href: string; label: string } }` would cover all 10 call sites structurally, but note it's genuinely two different visual variants (8 Notification-box sites + 2 plain-Text sites), and files 7/8 have identical dual-branch logic that could even share a slightly higher-level "PlayerNotLinked" pattern on top of the base component. No site has additional non-trivial JSX inside the notification itself beyond text/variable content, so the "message" prop as `ReactNode` is sufficient everywhere.</result>

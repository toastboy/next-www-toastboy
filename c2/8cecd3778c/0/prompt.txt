---

Putting a bearer-style invitation token into a query string increases the chance it gets leaked via referrer headers, proxy logs, analytics, or screenshots/bookmarks. If feasible, prefer a path segment (e.g. /footy/response/${token}) or a one-time opaque code exchanged server-side, and ensure downstream pages/routes are updated accordingly.

---

String-concatenating URLs can produce double slashes or malformed URLs depending on whether baseUrl ends with /, and it bypasses URL normalization. Consider constructing the link with new URL('/footy/response', baseUrl) and setting searchParams for token to make the result robust.

---

The token is interpolated into a URL path segment without encoding. If the token ever contains reserved URL characters (e.g. /, ?, #, %), the generated link can break or be ambiguous. Consider wrapping the token with encodeURIComponent(token) when building the path (similar to other call sites that already encode tokens).

---

The error telemetry hard-codes route: '/footy/contact', but this component is also rendered on other pages (e.g. /footy/info). This can misattribute client errors in observability. Consider passing the current route in via props (or deriving it where appropriate) so captureUnexpectedError logs the actual page route.

---

This captures all verification failures as 'unexpected', including likely expected domain errors (e.g., already-used/expired token). Consider capturing only truly unexpected errors (or using a different telemetry method/tag for expected failures) to reduce noise and improve alert quality.
